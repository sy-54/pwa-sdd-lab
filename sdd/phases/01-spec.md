# フェーズ1：SPEC（外部仕様）

入力：`requirements.md`　出力：`spec.md`（150行以内、雛形 `templates/spec.md`）

## 手順
1. `requirements.md` を読む。SDK がある環境では `sdk/README.md` も先に読む（何ができるかを知らないと、聞くべきことに気づけない）。
2. **実装が分かれる曖昧さ**を、次の観点ごとに書き出す（requirements から決まるものは除く）。
   - 初期値と初期状態／並び順／**一覧や集計に含める範囲**（全部か、今日・今月の分だけか）
   - 境界値と範囲外の入力／空・重複・不正な入力のときに何が起きるか
   - **その操作ができない状態で押されたとき**（対象が0件、手順の途中、順番が前後）
   - 削除などの取り消せない操作の確認／保存の単位と再読み込み後の状態
   - **手段が複数ある要求**（「知らせる」「分かる」「残す」をどの手段で実現するか）
3. 質問する。**1ラウンド最大5個**。書き出した曖昧さが5個を超えたら、残りは次のラウンドで聞く（2ラウンドまで）。答えで仕様が変わるものだけを、影響の大きい順に聞く。
   - 入力欄があるなら、**1ラウンド目に必ず**「不正な入力（空・0・範囲外・文字）のときどうなるか」を全入力欄まとめて1問で聞く。押せない状態のある操作があるなら、それも1問で聞く。
   - 選択肢つきで聞く（例：「0未満にできる？ A: できない（推奨） B: できる」）。
   - requirements に書いてあること、UI契約で決まっていることは聞かない。
   - 自動実行では質問を `questions.md` に書いて終了する。回答は `qa.md` に追記されて戻ってくる。質問がなければ `questions.md` に `NONE` とだけ書く。
4. 回答を「決定事項」に `D1: 内容（Q1）` の形で記録する。答えが出なかったものは「未決事項」に残し、**仮に採用した挙動**を併記する。
5. `spec.md` を書く。
6. lint を `--phase spec` で実行し、OK にする。人間に承認を求めて止まる。

## 書き方
- **画面と操作**：画面ごとに、見えるものと操作を箇条書きにする。**UI契約の全行（置くファイル、`data-testid`、表示形式）を漏れなく、言い換えずに写す**（パスと testid は lint が照合する）。追加する testid もここに書く。
- **振る舞い**：初期状態、状態の変化、保存と復元、並び順、上限と下限。
- **エラー時の挙動**：不正な入力、壊れた保存データ、権限の拒否、オフライン。「何を表示し、データをどうするか」まで書く。
- **受け入れ条件**：下の形式。Must の各項目に最低1つ。エラー時の挙動にも最低1つ。時間や日付で変わる表示には「時間が進んだ後に開き直す」AC を最低1つ。
- 聞かれていない機能を足さない。Won't に触れない。
- 実行環境の制約でできないこと（例：iOS ではサーバーなしで時刻指定の通知を出せない）は、質問の選択肢に「できない理由」を添えて早めに伝える。

```
### AC-01: 短いタイトル
- Given 前提（具体的な値で）
- When 操作（1つ）
- Then 画面で観測できる結果（testid と値）
```

良いAC：Then が「`count` に 2 と表示される」のように E2E でそのまま検証できる。
悪いAC：「正しく保存される」「使いやすい」（観測できない）。
