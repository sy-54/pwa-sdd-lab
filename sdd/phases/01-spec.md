# フェーズ1：SPEC（外部仕様）

入力：`requirements.md`　出力：`spec.md`（150行以内、雛形 `templates/spec.md`）

## 手順
1. `requirements.md` を読む。**実装が分かれる曖昧さ**を洗い出す（初期状態、境界値、空・重複・不正な入力、保存の単位、再読み込み後の状態、エラー時に何を見せるか）。
2. 質問する。**1ラウンド最大5個**。答えで仕様が変わるものだけを、影響の大きい順に聞く。
   - 選択肢つきで聞く（例：「0未満にできる？ A: できない（推奨） B: できる」）。
   - requirements に書いてあること、UI契約で決まっていることは聞かない。
   - 自動実行では質問を `questions.md` に書いて終了する。回答は `qa.md` に追記されて戻ってくる。質問がなければ `questions.md` に `NONE` とだけ書く。
3. 回答を「決定事項」に `D1: 内容（Q1）` の形で記録する。答えが出なかったものは「未決事項」に残し、**仮に採用した挙動**を併記する。
4. `spec.md` を書く。
5. lint を `--phase spec` で実行し、OK にする。人間に承認を求めて止まる。

## 書き方
- **画面と操作**：画面ごとに、見えるものと操作を箇条書きにする。UI契約の `data-testid` はそのまま使い、追加する testid もここに書く。
- **振る舞い**：初期状態、状態の変化、保存と復元、並び順、上限と下限。
- **エラー時の挙動**：不正な入力、壊れた保存データ、権限の拒否、オフライン。「何を表示し、データをどうするか」まで書く。
- **受け入れ条件**：下の形式。Must の各項目に最低1つ。エラー時の挙動にも最低1つ。
- 聞かれていない機能を足さない。Won't に触れない。
- 実行環境の制約でできないこと（例：iOS ではサーバーなしで時刻指定の通知を出せない）は、質問の選択肢に「できない理由」を添えて早めに伝える。

```
### AC-01: 短いタイトル
- Given 前提（具体的な値で）
- When 操作（1つ）
- Then 画面で観測できる結果（testid と値）
```

良いAC：Then が「`count` に 2 と表示される」のように E2E でそのまま検証できる。
悪いAC：「正しく保存される」「使いやすい」（観測できない）。
