`docs/LOOP.md` の手順だけに従って実行した。利用枠の制約で、ハーネスの実行は合計5回（Sonnet 2回・Haiku 3回）に絞った。

## 行ったこと
1. **課題を追加**：`tasks/T09-shopping/`（買い物リスト）を `tasks/T05-expense/` を参考に新規作成。`requirements.md` は lint（`--phase requirements`）を通した。曖昧さは4つ（追加位置、チェック済みの並び、数量の不正入力、商品名の空欄、削除確認）を `stakeholder.md` に残し、`acceptance/shopping.spec.ts` に13件（`[意図]` 5件）を書いた。

4. そこで、`results/improvements.md` に残っていた **未解決項目**（T07「めくる前に覚えた／まだを押したら」が、観点・手順を直した後も4実行連続で聞かれない）を今回の「直す」対象にした。LOOP.md の「普通は聞かないような細部なら検証」という基準に従い、`tasks/T07-flashcards/requirements.md` の UI契約にこの挙動を明記し、`acceptance/flashcards.spec.ts` のテスト名から `[意図]` を外した（曖昧さ→確定事項への分類替え）。
5. `npm run regrade -- T07`（ハーネス実行ではない）で既存5実行を採点し直し、点数が変化しないこと（＝採点ロジック自体は変えていない）を確認した。

9. `npm test`（68件）、`npm run summary` を実行。

## LOOP.md で分かりにくかった点
- **「実行」の数え方が曖昧。** 「ハーネスの実行は合計5回まで」という今回の指示と、LOOP.md 11行目の「1回のコマンドで流すのは8実行まで」を対応させる際、1回の `npm run harness` コマンドに複数モデル・複数課題を渡すと内部で複数の「実行」（課題×モデル×runs）が走る。何が1「実行」の単位かはログの `[T07-haiku-...]` 行から逆算して理解したが、LOOP.md 本文に明記されていれば迷わなかった。
- **`npm run regrade` がハーネス実行（モデル呼び出し）に数えるべきか不明。** 今回はモデルを呼ばない機械的な再採点なので実行回数に含めなかったが、LOOP.md にはその区別が書かれていない。
- **「検証」への分類替えの具体的な手続きが手順化されていない。** 「UI契約に書くか、テストを外す」とは書いてあるが、(a) `stakeholder.md` の該当行をどうするか（消す／残す）、(b) acceptance のテスト名から `[意図]` を外すべきか、(c) 既存実行の再採点が必要か、について明文化されていない。今回は要求者の意図行はそのまま残し（害がないため）、テスト名だけ変更し、`regrade` で無害であることを確認する、という手順を自分で決めた。
- **「効果を確かめる」の2回ずつ再実行が、利用枠が少ないときにどう縮退してよいか書かれていない。** 今回は1モデル1回ずつに縮退し、その旨をここに明記したが、LOOP.md 自体には縮退の指針（例：最低1回・次回必ず2回目を回す、等）がない。
- **課題追加時、既存の似た課題（今回は T02・T05）のうちどれを土台にすべきかの判断基準がない。** 「既存の課題（T02-todo が手頃）をコピー」と例示はあるが、入力検証つきの課題を作る際は T05 の方が近かった。複数の雛形がある場合の選び方を一言足すと親切。
